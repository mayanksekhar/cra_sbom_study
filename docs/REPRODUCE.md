# Reproducing the numbers

## What can be reproduced
The headline numbers can be recomputed from the summary files in this repository and, for the SBOM probes, from the data archive. The vulnerability databases (about 13 GB) are not published and cannot be rebuilt, because upstream data changes daily. Their file checksums are in tools/dbsnap_20261026.txt, tools/dbsnap_20261030.txt and tools/govuln_20261030.sha256. Running the full pipeline again would give different findings.

## Steps
1. Clone the repository. Run: python3 harness/check_all.py
   Expected without the archive: 8 ok, 0 failed, 2 skipped.
2. Obtain cra_data_20261117.tar.gz (not yet published, it will be attached to a release of this repository). Check it with: echo "c9f166ed2b4509e079db279a5df95bd2364572c155f93a3a5c8ccf30af55108f  cra_data_20261117.tar.gz" | sha256sum -c. The author builds it from the untracked files under results*/ with python3 -I harness/build_archive.py OUTDIR 20261117; the build sanitises the files, refuses to write anything if a trace is left, and gives the same hash on a second run.
3. Extract at the repository root without overwriting tracked files: tar -xzf cra_data_20261117.tar.gz --skip-old-files
4. Run again: python3 harness/check_all.py
   Expected with the archive: 10 ok, 0 failed, 0 skipped, and git status shows no changed files.

2. The regenerated docs/table_findings.md must equal the tracked file. The check reports DIFFERS if it does not.
3. The container set (results_containers) is checked from the tracked summary files and truth lists by harness/verify_containers.py. The image archives, SBOMs and scan outputs are not in the repository or in the data archive. They are rebuilt with harness/container_pull.sh (podman, images pulled by tag; the digests it records must equal those in results_containers/images.csv), harness/container_sbom.sh (Syft 1.45.1, Trivy 0.69.3 and cdxgen 12.9.0), harness/container_score.py, container_controls.py and container_components.py, with the frozen databases of tools/dbsnap_*.txt. Set TMPDIR to a folder on disk before running them: with /tmp on a RAM backed filesystem, cdxgen and Grype fail on the larger images (disk quota errors).
4. The older cdxgen replication (results_replication) is checked from two tracked CSVs by harness/verify_replication.py. To rerun it, use harness/replicate_cdxgen.sh VERSION WORKDIR (it installs that cdxgen release with npm into WORKDIR, separate from tools/, and runs it on fresh copies of the npm and Rust projects) and then harness/replicate_cdxgen_compare.py VERSION WORKDIR, which compares the purl sets with the pinned SBOMs in results_npm and results_rust. Versions run: 10.11.0 and 11.11.0. The older Grype replication is checked by the same script from four tracked CSVs (results_replication/replication_grype_VERSION.csv, 76 rows each) and results_replication/replication_grype_scores_0.88.0.csv. To rerun it, fetch a release with harness/fetch_old_grype.sh VERSION DEST (sha256 checked), scan with harness/replicate_grype.sh VERSION WORKDIR after source harness/env_frozen.sh, then run harness/replicate_grype_compare.py VERSION WORKDIR; harness/replicate_grype_scores.py VERSION SCRATCH_DIR compares the findings scores of a scratch copy of results_npm and results_rust scanned with 0.88.0. Versions run: 0.88.0, 0.90.0, 0.95.0 and 0.100.0 (0.97.0 on uptime-kuma only). The group field control (the Trivy SBOM of uptime-kuma with group merged into name and rescanned with 0.88.0, and the bisect over five releases) is harness/replicate_grype_group_control.py WORKDIR, run after source harness/env_frozen.sh from the repository root; its output is results_replication/grype_group_control_uptime_kuma.txt and verify_replication.py checks seven of its lines. The Trivy license control for nest (an unmodified copy and a copy with the one license list converted, both scanned with the pinned Trivy and the flags of gen_set.sh, compared with the corrected truth) is harness/replicate_trivy_license_control.py WORKDIR, run from the repository root after source harness/env_frozen.sh; its output is results_replication/trivy_license_control_nest.txt and verify_replication.py checks four of its lines.
4a. The older Syft and Trivy replication (results_replication/replication_syft_trivy.csv and syft_trivy_replication_record.txt) is checked by harness/verify_replication.py. To rerun it: bash harness/fetch_old_syft_trivy.sh WORKDIR (downloads Syft 1.33.0 and checks its checksum, builds Trivy 0.66.0 from the tagged source with Go), then bash harness/replicate_syft_trivy.sh WORKDIR OUTDIR, then python3 -I harness/replicate_syft_trivy_compare.py OUTDIR CSVFILE npm rust (the ecosystems to compare, which reproduces the tracked 38 rows) and python3 -I harness/replicate_syft_trivy_trace.py OUTDIR. It needs the source folders dataset/src_npm, src_npm2 and src_rust.
4b. The cdxgen replication on the eight npm projects added later: bash harness/replicate_cdxgen.sh VERSION WORKDIR npm2, then python3 -I harness/replicate_cdxgen_compare.py VERSION WORKDIR npm2 (writes replication_cdxgen_npm2_VERSION.csv in WORKDIR) and python3 -I harness/replicate_cdxgen_diff.py PROJECT WORKDIR VERSION. It is checked by harness/verify_replication.py.
4c. Go, Maven and PyPI with the older Syft and Trivy: bash harness/replicate_syft_trivy.sh OLDTOOLS OUTDIR go (or maven, pypi), then python3 -I harness/replicate_syft_trivy_compare.py OUTDIR CSVFILE go maven pypi. The Maven order control is harness/replicate_trivy_maven_control.sh OLDTOOLS WORKDIR. The Grype comparison on the Go Syft SBOMs is harness/replicate_syft_go_grype.sh OUTDIR WORKDIR followed by harness/replicate_syft_go_grype_compare.py WORKDIR CSVFILE (it needs the frozen database), and the purl mapping is harness/replicate_syft_go_forms.py OUTDIR. All of it is checked by harness/verify_replication.py.
5. The npm set is two lists: dataset/npm_set.csv (3 projects) and dataset/npm_set2.csv (8 projects chosen by the rule in docs/npm_selection.md with harness/probe_npm_candidates.sh; probe output in results_npm/probe.csv). Both are in results_npm and groundtruth_npm. harness/gen_set.sh reads CRA_WORK to move its work folder off a RAM backed /tmp (default /tmp/cra_work).

## Order of the pipeline (run by the author only, not by anyone else)
harness/fetch_set.sh, gen_set.sh, scan_set.sh, make_reference.py, score.py, score_findings.py, then the experiment scripts (vex_*.py, control_*.py, reach_*.py). They need the pinned tool versions in tools/pinned_versions.txt, the project sources at the pinned commits and the frozen databases.
