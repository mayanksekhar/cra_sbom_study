# Draft section 7 (2026-11-07): what an evidence grade SBOM and VEX pipeline must declare
Status: V verified in this repo, P partial, O open. Sources are files in this repository or the regulation and BSI texts read in this project. No legal interpretation and no legal advice. Statements describe three generators and three scanners at one version each, Go and Maven mainly.

Frame. Regulation (EU) 2024/2847 Annex I Part II point (1) asks for an SBOM covering at least the top level dependencies, and Article 13(8) requires vulnerabilities of the product including its components to be handled effectively. BSI TR-03183-2 v2.1.0 asks for more than the floor (recursive resolution to the first component outside the scope of delivery, section 5.1). [text read, docs/cra_mapping.md]

7.1 Declare the scope. A component list means different things under different scope policies, and the generator ranking flips between them. Maven, 8 projects, name level: against all scope truth cdxgen P 1.00 R 1.00 and Trivy R 0.48; against shipped truth without optional dependencies cdxgen P 0.48 R 1.00 and Trivy P 0.98 R 0.99. [V, results_mvn/metrics.csv] For compiled code BSI names the linker run, which matches our Go shipped truth. [text read; the match is my reading]

7.2 Carry the product's version in the purl, and make the version field agree. A missing version on the product made Grype report 108 findings against 53 with the tag (10 Go applications). [V] Trivy reads the version from the purl only, Grype and OSV Scanner read the version field first and fall back to the purl, and OSV Scanner treats UNKNOWN and latest like v0.0.0. A purl with the version and no conflicting field gives consistent results in all three. [V, 2 Go projects, harness/control_version3.py] Generators we ran leave the product without a version: Syft 0 of 43 SBOMs and Trivy 0 of 43 carry one, cdxgen 29 of 43 (the 14 without are the Go SBOMs, by count). [V, harness/bsi_probe.py] Mitigation tested for Syft on one project (fzf, Syft 1.45.1): --source-name and --source-version give the root a name and version (fzf, v0.56.0) but the purl stays null and the type stays file [V, one project]. cdxgen 12.9.0 with --project-name fzf --project-version v0.56.0 gives root name fzf, version v0.56.0, purl pkg:application/fzf@v0.56.0, against name github.com/junegunn/fzf, empty version and purl pkg:golang/github.com/junegunn/fzf without the flags [V, one project]. A purl of type application would probably not match ecosystem advisories for the product itself and loses the module path (untested). Trivy: no root name or version option seen in an 8 line grep of its fs options (inconclusive). Effect of the flags on root edges untested.

7.3 Never use a placeholder as a version. Syft wrote UNKNOWN in 79 version fields (64 Maven dependencies, 14 Go product modules, one by subtraction) and branch names in 6, cdxgen an empty version for 68 unpinned PyPI entries, Trivy no version for 15 Go product modules. [V counts] Consequence for findings: Syft's Maven SBOMs recovered 43 of 201 real findings, 38 of the misses on components without a usable version. [V, results_mvn] BSI Table 3 makes the version required for every component. [text read]

7.4 Connect the graph from the primary component and state completeness. Syft's primary component had no outgoing edge in 43 of 43 SBOMs, Trivy's had edges in 40, cdxgen's in 41; none of the 129 SBOMs states completeness through compositions. [V, harness/bsi_probe.py] For Trivy, a product scoped VEX statement removed findings only when the product and every component on the path to the vulnerable module had a purl: a library without a purl, an application without a purl and a file without a purl each removed 0 of 34, a library with a purl 34 (node_exporter v1.9.1). [V, one project, Trivy 0.69.3] BSI requires direct dependencies to be enumerated, empty entries for leaves, and completeness stated. [text read]

7.5 Resolve to what ships, and pin it. With no lockfile Syft listed no npm components for express (19 GitHub Actions components only) and Trivy listed none, and both found none of the 24 runtime components of five lockless PyPI projects, cdxgen found all. [V] cdxgen resolved newer versions than the pinned lock in ansible-lint and lost 19 of 80 PyPI reference findings. [V, one project] Trivy read Python requirements only from a requirements.txt style name (0 PyPI components from .config/requirements-lock.txt, 33 once copied). [P, one project, harness/control_trivy_layout.sh]

7.6 Write VEX statements scoped to the product. Product scoped statements: Trivy removed 353 of 353 not called findings and no called finding (10 Go projects), Grype removed 0 of 356; Grype honoured only module scoped statements (356 of 356). [V, results_go/vex_set.csv] Module scoped statements from one product suppressed reachable findings in another: 42 of 230 called findings were exposed, the prediction matched the scans of all 5 overlapping pairs. [V, Go set, shared dependencies inflate it] On the generators' own SBOMs, product scoped statements removed 0 or 1 of 34 findings on node_exporter. [V, one project] BSI names VEX and CSAF as the vehicle for the product level exploitability analysis. [text read]

7.7 Date the vulnerability data. Reference findings grew from 19 to 22 over four days with no change in the projects. [P, one measurement, pilot]

7.8 Account for findings on the product itself. 53 findings sit on the 10 Go applications' own modules at their tags (52 confirmed by Grype, Trivy and OSV Scanner, 18 high or critical); generators exclude the root from the component list, so they are outside the inventory. [V, results_go/product_findings.csv] Three of the four projects with none have no database record. [V]

7.9 State the method and its limit when claiming reachability. Reachability would remove 356 of 608 Go findings (59 percent) by one oracle (govulncheck, Go only); manual labels 0 of 40. [P] The Article 3(41) definition of exploitable vulnerability is the regulation's own bar, and the regulation names no method. [text read]

Not claimed: any legal reading of how Annex I Part I 2(a) or Article 13(8) applies to component vulnerabilities; any rate beyond the sets studied; any statement about other tool versions.
