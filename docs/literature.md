## Full reads (2026-10-30)

Mind the Gap (arXiv 2609.19920, Inria and ANSSI): 3,000+ JS and Rust projects, lockfile baseline that keeps dev and test dependencies, generation only, no vulnerability scanning. Covers scope policy, cdxgen directory exclusions, symlink and workspace placeholder components, aliasing. Plans an edge case benchmark and Python and Java extension. Tool versions Syft 1.38.2, Trivy 0.68.2, cdxgen 12.0.0. Our npm and Rust RQ1 results are replication.

Hidden Dependencies (arXiv 2604.21278): Java, synthetic, one vulnerability. With VEX applied, Grype and CVE-Bin-Tool suppress nothing, Trivy suppresses everything including reachable cases (false suppression). Cloned components not detected in CycloneDX by any tool. Measures consistency, not accuracy. Same Trivy version (0.69.3) as our setup.

Revised direction: From SBOM to finding, where correctness is lost. Layers: SBOM scope and identity (extend to Go, Maven, Python), scanner consumption (phantom matches, versionless components, feed coverage, drift, crashes), VEX application on real findings. CRA discussion: what an evidence grade pipeline must declare.

## Read in full 2026-11-10 (arXiv HTML and PDF)
Zhou, Dacier, Konstantinou, A Reality Check on SBOM-based Vulnerability Management, CODASPY 2026, arXiv 2511.20313, doi 10.1145/3800506.3803490. 2,414 repositories in Python (Poetry), Rust, Ruby, PHP. Syft 1.33.0 and Trivy 0.66.0 identical and 100 percent accurate from lock files (Jaccard 1.0); both empty for package-lock.json at those versions. Manual check of 16 repositories, 113 reported, 9 confirmed (92.0 percent false positive rate), coverage check removes 61.9 percent. An earlier version quoted 97.5 and 63.3 percent in a search summary. Go: 12 projects at 2025 release versions, 121 reported, 31 with listed symbols present in the compiled binary's symbol table (74.4 percent reduction), symbols from the Go vulnerability database; no call graph, no govulncheck. States that VEX is a communication format, not an analysis engine. Threats: fixed environment, manual verification limited, static analysis only, vendoring not addressed.
Shi et al., VEX-Bench, arXiv 2609.08040. 75 expert labelled cases, Go 30, Java 25, Python 20; Fleiss kappa 0.667 on 15 calibration cases; 70.7 percent not affected, code_not_reachable 38 of 75. Table 3: OSV-Scanner F1 40.5, Trivy 36.1 (n 75); Go subset: OSV detect F1 38.9, OSV reachability 42.9 (precision 28.6, recall 85.7), govulncheck coverage 63.3 percent (19 of 30, needs a successful build), precision 22.2, recall 28.6, F1 25.0. Affected predicted if a tool reports the target CVE. Reachability does not imply exploitability.
Read only as abstract, html summary or poster: Churakova, Ekstedt, Schmid, Vexed by VEX tools, arXiv 2503.14388 (seven tools, Jaccard and Tversky, highest pairwise Jaccard about 0.69 Trivy against Grype, 88 percent correlation with database overlap).
Seen as titles only, to read: A Practical Solution to Systematically Monitor Inconsistencies in SBOM-based Vulnerability Scanners (arXiv listing, 2025-12); LUCID, a framework for reducing false positives and inconsistencies among container scanning tools; and works cited by Reality Check: Yu et al. DSN 2024 (metadata based SBOM correctness), O'Donoghue et al. 2023 and 2024, Rabbi et al. SAC 2024 (npm), Benedetti et al. arXiv 2409.06390 (Python), Balliu et al. 2023 (Java), Cofano et al. TrustCom 2024 (Python), Zhao et al. ISSRE 2024 (CovSBOM), Pashchenko et al. TSE 2022 (Vuln4Real), Imtiaz et al. ESEM 2021.
govulncheck documentation (go.googlesource.com, doc.go, seen as a snippet): binary mode uses the binary's symbol information to find mentions of vulnerable functions and may report false positives for code that is in the binary but unreachable; govulncheck can emit OpenVEX. Our mechanical check is close to that mode. Binary mode might fit in memory for k9s (untested).

## Read in full 2026-11-10 (second batch)
Churakova, Ekstedt, Schmid, Vexed by VEX Tools, arXiv 2503.14388 v3 (html). Seven tools (Trivy, Grype, DepScan, Docker Scout, Snyk, OSV-scanner, Vexy), 25 configurations (20 generator and scanner combinations plus 5 direct image scans), 48 Docker Hub images (32 random, 8 non vulnerable, 8 vulnerable), CycloneDX 1.4 and SPDX 2.3. Highest pairwise Jaccard 0.694 Trivy against Grype, general similarity of all tools 0, highest Tversky for five tools 3.4 percent. Pearson correlation 0.88 between database overlap (by database name) and report similarity. SBOM quality ruled out as the explanatory factor in that setting; OSV and Vexy reports have no status field. Studies generation of affected vulnerability lists, not VEX consumption. Text says the best pair on identical SBOMs does not exceed 70 percent while tables 7 to 10 show Trivy against Grype at 0.026 to 0.101 (inconsistency inside the paper, not resolved).
Rosso, Jaffar, Brighente, Conti, SVS-TEST, SAC 2026, arXiv 2512.17710, artifacts doi 10.5281/zenodo.17921254. Tools: Bomber 0.5.1, Dependency-Track 4.12.0, dep-scan 5.4.6, Grype 0.87.0, snyk-cli 1.1295.2, FOSSA 4.27.43, Vulert 2.x. 16 crafted SBOMs in 8 scenarios (component identifier support, CPE without version, purl without version, identifier priority, no identifier, non canonical purl, CycloneDX VEX, invalid input). Findings: Grype and dep-scan use the CycloneDX version field and ignore the version in the purl (silent failure without it); Dependency-Track and snyk-cli use the version in the purl; Grype 0.87.0 never looked up components without a version; purl without a version passed only in Bomber, FOSSA, Vulert; FOSSA looks up only components with a purl; one embedded CycloneDX VEX case suppressed only in Dependency-Track; Grype warned that it does not support the CycloneDX VEX format. 22,320 purl entries without a version in the Wild SBOM dataset (Soeiro et al.). Table 4 lists Grype PR 2591 (empty versions meet version constraints, impact not confirmed). Not tested there: Trivy, OSV Scanner, conflicting version carriers, product scoped VEX, generators.
Seen as titles in reference lists, to read: Dann et al. TSE 2022 (OSS vulnerability scanners test suite), Halbritter and Merli ARES 2024.
One search for work after October 2026 (2026-11-10): nothing newer than September 2026 (Mind the Gap, VEX-Bench).

## Read in full 2026-11-13 (third batch, through the fetch tool, which returns a summary of the page text; figures to be checked against the PDFs before they are cited)
O'Donoghue, Boles, Izurieta, Reinhold, Impacts of SBOM Generation on Vulnerability Detection, SCORED 2024. 100 most pulled Docker Hub images, up to 25 tags each, 2,313 images started and 1,303 SBOMs per corpus after exclusions; Syft v0.102.0 and Trivy v0.49.0 generate, CycloneDX 1.5 and SPDX 2.3; Trivy v0.49.0, Grype v0.74.3 and CVE-bin-tool v3.2.1 analyse. No ground truth. Only 12 percent of Trivy analysed CycloneDX SBOMs gave the same count across generators (Grype 2 percent); Trivy analysis of Trivy generated SBOMs was consistent across formats in 83 percent, of Syft generated ones in 19 percent. 43.7 percent of images were excluded, mostly through CVE-bin-tool failures.
Benedetti, Cofano, Brighente, Conti, arXiv 2409.06390. 1,000 PyPI packages; cdxgen, GH-sbom, ORT, Syft, Trivy; Grype scans; ground truth from pip freeze and pip-audit. Jaccard 49.77 (cdxgen), 36.50 (ORT), 26.33 (Syft), 23.63 (Trivy), 23.98 (GH-sbom); the proposed pip based generator reaches 78.39. The abstract and table figures do not fully agree (flagged by the fetch tool).

Yu, Song, Hu, Yin, On the Correctness of Metadata based SBOM Generation, DSN 2024. 7,876 repositories in nine languages; Trivy 0.43.0, Syft 0.84.1, sbom-tool 1.1.6, GitHub dependency graph; differential analysis, ground truth for requirements.txt only (recall 0.10 and precision 0.25 for Trivy and Syft, 0.73 and 0.74 for sbom-tool); 46 percent of requirements.txt dependencies are pinned; no vulnerability findings scored.
