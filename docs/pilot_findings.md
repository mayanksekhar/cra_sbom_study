# Pilot findings (descriptive, 10 projects, not statistical evidence)

Tools: Syft 1.45.1, Trivy 0.69.3, cdxgen 12.9.0. Projects: 2 each for Go, Maven, npm, PyPI, Rust.
Scoring: purl normalized, root project and workspace members excluded, GitHub Actions components excluded.

## Verified

1. The definition of truth changes the ranking. For node_exporter at name plus version, F1 against declared, resolved and shipped (3 platforms) truth is: cdxgen 0.92, 0.75, 0.99; Syft 0.96, 0.87, 0.90; Trivy 1.00, 0.83, 0.93.
2. Lockfile dependence. Express without a lockfile: Syft 0 components, Trivy 0, cdxgen 368. With a lockfile, Syft and Trivy match the 64 shipped packages exactly.
3. Scope policy differs by tool. cdxgen includes dev dependencies (npm) and all Maven scopes (171 and 40 artifacts). Trivy matches runtime scope on Maven (105 of 106 and 2 of 2). Syft and Trivy drop npm dev dependencies.
4. Scope leakage from nested manifests. axios ships 26 packages from its root lockfile, but Syft and Trivy report about 205 from 6 lockfiles (docs site, tests). Same pattern in ripgrep (fuzz/Cargo.lock) and flask (examples/celery/requirements.txt).
5. Syft on Maven reads direct dependencies only (28 of 171 artifacts on petclinic) and gives no version for 25 of those 28.
6. Python with a lockfile: all three tools find 7 of 7 runtime packages in flask but report 98 (Syft), 78 (cdxgen) and 29 (Trivy) components in total. Without a lockfile (requests), Syft and Trivy find 0 of 4 runtime packages and cdxgen finds 4 of 4 plus 50 extras.
7. Syft adds GitHub Actions components (6 to 28 per project) to product SBOMs.
8. cdxgen resolves for the host platform only. Its 46 Go modules equal the linux amd64 binary, and the 47th module (lufia/iostat) appears only for other targets.
9. Syft and Trivy list the root project as a component with an empty version on Go.

## Method caveats

1. cdxgen agreement on Maven, npm and Rust is partly circular, because truth comes from the same package managers.
2. Express lockfile was generated by us (recorded in groundtruth/npm/express_lockfile.txt).
3. Truth for requests (no lockfile) depends on the resolution date. Use name level for it.

They are in the resolved graph, so they are true components, but the recorded location evidence is wrong. Mechanism not verified.

3. Whether Trivy limits uv.lock to runtime packages (inferred from counts only).

## VEX experiment (node_exporter, 3 findings that govulncheck says are not called, frozen DBs 20261030)

Setup: reference SBOM of node_exporter (root component, dependency graph added) and a second SBOM other_app containing the same two modules. OpenVEX form A: product is the application, subcomponent is the vulnerable module. Form B: product is the vulnerable module. Grype 0.114.0, Trivy 0.69.3.

Verified:
1. Without a dependency graph in the SBOM, Trivy did not apply form A. With root to component edges, Trivy applied form A to node_exporter only (0 left, other_app 3 left). The first flat SBOM result was an artifact of my SBOM, not Trivy behaviour.
2. Grype ignored form A in both runs (3 left, 0 ignored on both SBOMs).
3. Form B suppressed all 3 findings in both scanners on both SBOMs. By the OpenVEX spec the statement is about the module as product, so this is an authoring hazard, not proven false suppression. It becomes false suppression only if a product containing the module calls the vulnerable code (control program pending).
4. The same correct VEX file leaves different residual findings depending on the scanner (Trivy 0, Grype 3) and on whether the SBOM carries a dependency graph.

Not tested: an intermediate library as product (the scenario in Hidden Dependencies), OSV Scanner VEX support, other VEX formats.

## VEX control experiment (positive control for false suppression)

Control: dataset/controls/other_app calls html.Parse and html.Render from golang.org/x/net v0.61.0. govulncheck (frozen Go DB) reports it affected by GO-2026-6860 and GO-2026-6866, so the findings are real and reachable.

Verified (Grype 0.114.0, Trivy 0.69.3, SBOM with dependency graph):
1. No VEX: 2 findings in both scanners.
2. Form A (product is node_exporter): 2 left in both. Correctly not applied to a different product.
3. Form B (product is the module): 0 left in both. Both reachable findings suppressed. This is false suppression, demonstrated on one constructed control.
4. Form B is arguably a badly scoped statement, but it is what a pipeline produces when it turns one product's reachability result into a module level statement, and neither scanner restricts it to the analysed product.

Not shown: a rate. Needs many findings (older release pins), an automated VEX generation step, and govulncheck as oracle per finding.

## Cross project VEX suppression (Go set, 10 applications, module scoped form B, frozen DBs 20261030)

Static prediction: a called finding of project Q is covered if another project P's module level file marks the same module version and advisory not called. 5 of 90 ordered pairs overlap; 42 of 230 called findings (18 percent) are covered by some other project's file (cli 14, hugo 15, k9s 13). Mostly golang.org/x/crypto v0.22.0 advisories.
Scans of the 5 pairs: the prediction matched exactly in both scanners (hugo to cli 14, nats-server to cli 14, blackbox_exporter to k9s 13, cli to hugo 13, helm to hugo 2 called findings removed by Trivy and Grype). Product scoped form A removed 0 in all pairs (Trivy).
Verified: module scoped VEX statements from one product silently suppress reachable findings in another product that shares the module version and advisory. This is the form Grype requires.
Caveat: exposure depends on shared module versions across products (several projects here share Prometheus and other dependencies). A more varied set could show less.
Unclassified findings on the corrected SBOMs: Trivy 74 (52 on the product's own module, 22 elsewhere), Grype 75 (53 and 22). Correction: with a versioned root purl Trivy does report advisories on the product's own module. The 22 elsewhere are caddy findings on go-chi/chi and go-jose with CVE aliases only, so reach.json gave no verdict.
